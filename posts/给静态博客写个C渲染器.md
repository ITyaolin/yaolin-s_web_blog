# 给静态博客写个 C 渲染器

这个博客没有后台、没有数据库、也没有构建工具，文章就是 `posts/` 里的 `.md` 文件。本地写、本地看，一切都很舒服——直到我把它推到静态托管上。

## 问题是这样的

站点本来是这样列文章的：首页去请求 `posts/` 这个目录，读服务器返回的目录列表，把里面的 `.md` / `.txt` 挑出来。本地 `python3 -m http.server` 能看到目录列表，所以写完刷新就出现；但 GitHub Pages 不会给你列目录，请求回来是一个 404。

结果就是：文章还在，首页空了。

## 两条路，都走通

我没有推翻原来的设计，而是补了两层：

- 渲染一份清单 `posts.json`，首页拿不到目录列表时就用它列文章
- 把每篇文章预先渲染成静态网页 `posts/p-<id>.html`，推送时一起带走

这样本地服务器照旧实时读文件夹（写完刷新就见效），静态托管则走预渲染页，两条路各自都能用、互不干扰。

## 最关键的一条：规则要完全一样

同一篇文章，浏览器里 `post.html?id=xxx` 渲染一遍、C 程序再渲染一遍，只要两边规则有一点点不一样，就会出现「本地看是对的，推上去歪了」。所以 `tools/render.c` 并不是重新实现一套 Markdown，而是把前端那套逐条照搬过来：

- front matter 的解析：`title` / `date` / `tags` / `summary`，`tags` 还支持 `[a, b]` 写法
- Markdown 子集的渲染顺序：行内代码占位 → 加粗 → 斜体 → 删除线 → 图片 → 链接 → 还原占位
- 没有 `summary` 时的自动摘要：96 个 UTF-16 单元，超出部分补省略号
- 阅读时长：中文 400 字/分、英文 180 词/分，至少 1 分钟
- 封面：对文章 id 做一次 hash，再从壁纸池里取一张

最后一条我特意没把壁纸列表抄进 C 里，而是启动时去读 `js/store.js` 里那个数组。抄一份下来，迟早会忘了同步。

## 页面放在 posts/ 里，靠一行 base 救回来

文章页和文章源文件放在同一个目录（`posts/`），推送后一眼就能对上。代价是页面深了一层，页面里那些 `css/…`、`js/…`、`img/…`、`l2d/…`、`music/…` 的相对路径全都会找错地方。

我没有把它们逐个改写成 `../`，而是在 `<head>` 里加了一行：

```html
<base href="../">
```

所有相对路径就都锚回站点根目录了，生成页和 `post.html` 用的是同一套引用。副作用有一个：`<base>` 会连纯 `#fragment` 一起改掉，页内跳转的 `#sec-1` 会跑到站点根去，所以目录里的锚点必须写成完整路径 `posts/p-<id>.html#sec-1`。

## 幂等，所以敢挂在推送前

渲染器只在内容真的变了才写文件，没变的页一动不动。于是有了三个开关：

```sh
make            # 编译渲染器（只需要一次）
make render     # 渲染：posts/p-<id>.html + posts.json
make check      # 只检查有没有忘记渲染，过期就退出码 1
make prune      # 删掉源文章已不存在的旧静态页
```

`make check` 是我最喜欢的一个：退出码非 0，就能直接串进推送流程，「忘记渲染」这件事从此不会发生。

```sh
vim posts/新文章.md
make render && make check
git add -A && git commit -m "新文章" && git push
```

## 顺手清掉的历史包袱

文章页最早生成在站点根目录（和 `index.html` 同级），因为那时候只有同层才能让相对路径正常工作。现在有了 `<base>`，`make render` 会把根目录里那些旧位置的页面自己删掉，清理逻辑只认带生成标记的 `p-*.html`，不会误伤手写的页面。

## 一点体会

写这个小工具，最大的收获其实不是 C，而是「对齐」：把浏览器里那套逻辑当作唯一正确的标准，C 只做它的等价实现，两边输出逐字节对比通过才算完。规则一致了，渲染这件事才真的能无脑压进一条命令里。
